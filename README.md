# IDC 운영 도구 모음

데이터센터에서 11년 9개월 동안 상주 운영을 하며 "이건 도구가 있었으면 좋겠다"고
생각한 것들을 직접 만든 기록입니다. 다섯 개 모두 실제 운영에서 겪은 문제에서
출발했고, 각 폴더의 첫머리에 그 문제를 적어 두었습니다.

파이썬 도구는 표준 라이브러리만 씁니다. 점검 대상 서버에 패키지를 설치할 수 없는
경우가 많고, 설치를 요구하는 순간 점검이 밀리기 때문입니다.
HTML 도구는 단일 파일이라 브라우저로 열면 바로 돌아갑니다.

| 폴더 | 도구 | 무엇을 해결하려고 만들었나 |
|---|---|---|
| `01-noc-dashboard` | IDC 상면 관제 콘솔 | 장비 목록과 랙 환경, 포트 상태를 한 화면에서 보고 싶었다 |
| `02-server-healthcheck` | 서버 헬스체크 | 매일 아침 손으로 하던 점검을 스케줄러에 맡기고 싶었다 |
| `03-ops-scripts` | 운영 스크립트 5종 | 로그 급증·디스크 임계·서비스 정지·백업 누락·인증서 만료를 미리 알고 싶었다 |
| `04-linux-security-lab` | 리눅스 보안 실습 | 정보보안기사를 준비하며 정리한 내용을 직접 조작해 보고 싶었다 |
| `05-backup-simulator` | 백업 운영 시뮬레이터 | 백업 스케줄이 왜 그렇게 짜였는지 설명할 수 있게 되고 싶었다 |
| `06-incident-lab` | IDC 장애 대응 랩 | 조치보다 먼저 무엇을 확인하는지를 연습하고 싶었다 |
| `07-server-console` | 서버 운영 콘솔 | 같은 명령의 결과가 장애에 따라 어떻게 달라지는지 보고 싶었다 |
| `08-network-path` | 네트워크 경로 진단 | 어느 구간에서 끊기는지에 따라 조치가 달라지는 것을 정리하고 싶었다 |

## 01. IDC 상면 관제 콘솔

`01-noc-dashboard/noc-dashboard.html` — 브라우저로 열면 됩니다.

4개 랙에 배치된 13대의 장비를 랙 단위로 보여 줍니다. 장비를 누르면 CPU·메모리·흡기
온도와 포트별 상태가 열리고, 포트를 차단·해제하면 트래픽과 상태가 함께 바뀝니다.

랙 하단에 흡기 온도와 랙 전력을 둔 이유가 있습니다. 운영하면서 서버 자원만 보다가
랙 전력 한계에 걸려 신규 입주를 못 받는 상황을 겪었기 때문입니다. 장비 상태가 모두
정상이어도 랙이 6kW를 넘으면 그 랙에는 더 넣을 수 없습니다.

포트 이름은 장비 유형별 실제 규칙을 따랐습니다. 라우터는 `GigabitEthernet` /
`TenGigE`, 방화벽은 `port1 (outside)` / `port2 (inside)` / `port5 (ha)`,
서버는 `bond0` / `idrac·ilo`입니다.

## 02. 서버 헬스체크

```bash
python3 healthcheck.py --config check.json
echo $?          # 0 정상 / 1 주의 / 2 조치 필요
```

호스트 정보와 업타임, CPU 부하, 메모리, 파일시스템별 사용률, 지정 서비스 구동 여부,
네트워크 도달성, 메모리 상위 프로세스를 점검하고 날짜별 로그로 남깁니다.
리눅스와 윈도우에서 모두 돌아가며, 윈도우에서는 PowerShell을 호출해 같은 항목을 봅니다.

종료 코드를 나눈 것이 핵심입니다. cron이나 작업 스케줄러가 판단할 수 있어야 사람이
매일 열어보지 않아도 됩니다.

리눅스 CPU 판정은 로드 애버리지를 코어 수로 나눠 환산합니다. 코어가 32개인 서버에서
로드 8은 정상인데, 코어를 보지 않으면 경보가 됩니다.

## 03. 운영 스크립트 5종

```bash
python3 log_analyzer.py /var/log/messages --top 10 --sigma 2.0
python3 disk_forecast.py --threshold 90 --alert-days 30
python3 svc_watchdog.py nginx sshd --max-restarts 3
python3 backup_verify.py manifest.json --record   # 최초 1회
python3 cert_expiry.py --file domains.txt --warn 30 --crit 7
```

**log_analyzer** — 건수가 많은 오류만 보면 갑자기 늘어난 오류를 놓칩니다.
그래서 유형별 집계와 시간대별 분포를 함께 봅니다. 타임스탬프·PID·IP·경로·숫자를
치환해 같은 원인의 로그를 하나로 묶습니다. 이 정규화가 없으면 같은 오류가 수백 개의
서로 다른 문자열로 흩어져 집계가 의미를 잃습니다.

**disk_forecast** — 디스크 경보는 90%를 넘은 뒤에 울립니다. 그때는 이미 야간이고
지울 것을 찾을 시간이 없습니다. 매일 사용률을 JSON에 쌓아 두고 최소제곱 직선으로
임계 도달일을 계산합니다.

**svc_watchdog** — 무조건 재기동하는 워치독은 위험합니다. 원인이 남아 있는데 계속
살려 두면 문제가 감춰집니다. 재기동 간격을 5초→15초→45초로 늘리고, 창 안에서 3회를
넘으면 멈추고 사람을 부릅니다.

**backup_verify** — "백업 잡이 성공했다"와 "복구할 수 있는 파일이 있다"는 다릅니다.
존재·크기·신선도·SHA-256 네 가지를 따로 봅니다. 잡은 성공인데 0바이트이거나 어제
파일이 그대로 남아 있는 경우를 걸러내기 위해서입니다.

**cert_expiry** — 인증서 만료는 예고 없이 오지 않는데도 흔한 중단 원인입니다.
담당자가 바뀌거나 자동 갱신이 조용히 멈춰 있으면 만료 당일까지 아무도 모릅니다.

## 04. 리눅스 보안 운영 실습

`04-linux-security-lab/linux-security-lab.html`

세 가지 탭이 있습니다.

- **권한 계산** — 체크박스로 8진수와 기호 표기를 확인합니다. setuid·setgid·sticky를
  포함하며, 실행 비트가 없는 setuid가 대문자 `S`로 표시되는 것까지 반영했습니다.
  umask는 빼는 값이 아니라 끄는 비트라는 점을 계산으로 보여 줍니다.
- **로그 판별** — secure 로그 12줄에서 공격 흔적을 고르고 채점합니다. 계정 대입,
  침입 성공, 권한 상승, UID 0 계정 생성, 비인가 포트 대기가 순서대로 들어 있고,
  정상 배포 접속과 OOM 종료가 섞여 있습니다. 오탐도 함께 채점합니다.
- **방화벽 정책 검토** — 접수된 요청 8건 중 그대로 넣으면 위험한 줄과 이유를 보여
  줍니다. 요청을 그대로 반영하지 않고 되묻는 일이 방화벽 관리의 실제 업무입니다.

## 05. 백업 운영 시뮬레이터

`05-backup-simulator/backup-simulator.html` — 상단의 하루·일주일·한 달 버튼으로
날짜를 진행시킵니다.

정책 3개(WAS 파일시스템, Oracle RMAN, 파일 서버)에 대해 평일 증분, 주말 풀,
월말 풀 스케줄을 생성하고 실행합니다. 주말 풀을 토·일로 나눈 이유는 같은 스토리지
유닛을 동시에 점유하지 않기 위해서입니다. 월말 풀은 보관 기간이 길어 테이프로 보내며,
정규 창으로는 세 정책이 순차 실행되지 않아 확장 창(18:00–08:00)을 씁니다.

차등 증분과 누적 증분의 차이를 복구 체인 탭에서 확인할 수 있습니다. 차등은 마지막
풀 이후의 증분을 모두 필요로 하고, 누적은 풀과 최근 증분 하나만 있으면 됩니다.

장애 주입 4종이 있습니다. 디스크 풀 고수위(129), 스크래치 볼륨 소진(96),
미디어 서버 정지(219), 클라이언트 처리량 저하(196 유발)입니다. 상태 코드마다
재시도 가능 여부와 먼저 확인할 것을 함께 적어 두었습니다.

## 06. IDC 장애 대응 랩

`06-incident-lab/incident-lab.html`

세 가지 탭이 있습니다.

**장애 대응** — 접수된 장애 6건 중 하나를 고르고, 조사 항목을 눌러 정보를 모은 뒤
원인을 판단하고 조치를 선택합니다. 채점은 세 가지를 봅니다.
원인과 조치가 맞았는지, 필요한 조사를 다 했는지, 불필요한 조사를 몇 건 했는지입니다.
조사를 건너뛰고 조치를 골라도 통과할 수 있게 두었습니다. 현장에서도 확인 없이 조치하는
일이 생기고, 그때 어떤 근거가 빠졌는지 보여 주는 편이 낫다고 생각했습니다.
통과하면 발생 시각, 조사 경로, 원인, 조치, 재발 방지가 담긴 장애 보고서가 만들어집니다.

| 시나리오 | 증상 | 원인 |
|---|---|---|
| S1 | 웹 접속 불가, ping은 정상 | 어제 정책 정리에서 443 규칙이 함께 삭제됨 |
| S2 | IP는 되는데 도메인만 실패 | 신규 서브도메인 A 레코드 등록 누락 |
| S3 | APP01 CPU 98%, 응답 2초→15초 | 야간 배치와 온라인의 커넥션 풀 경합 |
| S4 | DB01 디스크 97% | trace·audit 로그 급증 |
| S5 | 랙 흡기 23도→31도 | 해당 랙 담당 항온항습기 냉수 계통 이상 |
| S6 | 배치 지연 연쇄, 마감 2시간 46분 전 | 처리 건수가 평소의 3.6배로 증가 |

오답 조치에도 결과를 붙였습니다. S3에서 APP01을 재기동하면 풀은 초기화되지만
배치가 계속 돌아 몇 분 뒤 같은 상태가 되고, S5에서 경보 임계치를 35도로 올리면
문제가 보이지 않게 될 뿐입니다. 무엇을 하지 말아야 하는지가 더 중요한 경우가 있습니다.

**감시 기준** — 임계치를 바꾸면 판정과 트리거 발화가 다시 계산됩니다.
감시 대상 8대 중 실제 조치가 필요한 것은 3대입니다.
기본값에서는 5건이 발화해 오탐 2건이 섞이고, 느슨하게 잡으면 발화가 3건으로 줄지만
1건을 놓칩니다. 빡빡하게 잡으면 놓치는 것은 없지만 오탐이 5건으로 늘어납니다.
임계치를 정하는 일이 이 둘 사이의 선택이라는 것을 숫자로 보이려고 만들었습니다.

**변경 요청 처리** — 고객사 방화벽 정책 요청을 접수부터 종료까지 9단계로 진행합니다.
4단계가 이 절차의 핵심입니다. 원래 요청은 "WEB 대역 전체 → APP 대역 전체"였고,
필요한 통신이 단일 구간임을 확인해 /32로 좁힙니다. 요청을 그대로 넣지 않고
되묻는 것이 방화벽 관리의 실제 업무라고 생각합니다.

## 07. 서버 운영 콘솔

`07-server-console/server-console.html`

서버 6대(리눅스 5, 윈도우 1)를 골라 명령을 실행합니다. 리눅스는 `top` `free -m`
`df -h` `ps aux` `systemctl status` `ss -tlnp` `tail` `ip a`, 윈도우는 `Get-Process`
`Get-Volume` `Get-Service` `Get-NetTCPConnection` `Get-EventLog`를 씁니다.
직접 입력할 수도 있고, `df`만 쳐도 `df -h`로 이어집니다.

장애 5종을 켜면 서버 상태 자체가 바뀝니다. 명령 출력은 상태에서 만들어지므로,
`nginx`를 정지시키면 `systemctl status`가 failed로 바뀌는 동시에 `ps`에서 프로세스가
사라지고 `ss`에서 80·443 포트도 함께 사라집니다. 한 곳만 고쳐 둔 화면이 아니라
상태를 바꾸고 결과를 파생시킨 이유는, 명령 사이의 앞뒤가 맞아야 연습이 되기 때문입니다.

## 08. 네트워크 경로 진단

`08-network-path/network-path.html`

Internet → FW-01 → L4-01 → WEB01/02 → APP01 → DB01 구성에서 장애를 넣고
어느 구간에서 끊기는지 찾습니다. 장애는 방화벽 443 차단, DNS 레코드 삭제,
L4 멤버 다운, 라우팅 누락, MTU 불일치 다섯 가지이고 동시에 켤 수 있습니다.

만들면서 가장 신경 쓴 것은 **장애가 있어도 다른 명령은 정상으로 나오게 하는 것**입니다.

- 방화벽 443이 막혀도 ping은 성공합니다. ping만 보고 정상이라 판단하면 놓칩니다.
- DNS 레코드가 없어도 IP + 포트로는 붙습니다.
- L4 멤버가 DOWN이어도 그 서버 자체는 ping에 응답합니다.
- 라우팅이 없어도 앞 구간은 전부 정상입니다.

한 가지 명령만으로는 구분되지 않게 만들어야 순서대로 좁히는 연습이 됩니다.
장애를 짚었다고 생각하면 원인을 골라 제출하고, 여러 개를 동시에 켠 경우
전부 맞혀야 통과합니다.

## 검증 기록

만들면서 확인한 내용입니다.

**백업 시뮬레이터 — 깨진 설계를 세 번 고쳤습니다**

처음 70일을 돌렸을 때 두 가지가 깨졌습니다. 디스크 풀 24TB로는 35일 보관을 감당하지
못해 129가 55건 발생했고, 월말 테이프 백업이 정규 창 안에 끝나지 못해 196이 났습니다.
용량을 48TB로 올리고 월말 확장 창(18:00–08:00)을 도입해 70일 전건 성공으로 바꿨습니다.

그런데 365일로 늘려 다시 돌리자 96(스크래치 풀 소진)이 6건 나왔습니다. 원인은 제
테이프 모델이 틀렸던 것입니다. 1,200GB를 넘는 백업 1건이 볼륨 1개를 통째로 쓰도록
만들어 두었는데, 실제 LTO-9 볼륨 하나는 18TB이고 사용량이 볼륨 용량을 넘을 때
다음 볼륨으로 넘어갑니다. 12개월이면 24개가 필요해져 보유 12개로는 모자랐던 것입니다.
여유 볼륨을 건수가 아니라 사용량에서 파생시키도록 고쳤습니다.

```
365일 후 — 상태 코드 {"0": 120}
디스크 풀 82.1% / 고수위 90%
테이프 여유 볼륨 8/12
카탈로그 121건 · 백업 ID 중복 0건
```

복구 체인은 경계 조건까지 확인했습니다. 풀 직후에는 필요한 이미지가 1개이고,
풀이 없는 시점을 조회하면 복구 불가를 반환하며, 없는 정책은 null을 반환합니다.
누적 증분은 어떤 경우에도 2개를 넘지 않고, 차등은 항상 누적보다 같거나 많습니다.

장애 주입은 각각이 실제로 발생하는 날에 확인했습니다. 평일에는 테이프 잡이 없어
96이 나오지 않고 증분은 작아 196이 나오지 않는 것이 정상이므로, 월말과 주말에
나눠 검증했습니다.

```
월말 09-30 + 스크래치 소진   → 3건 모두 96
토요일 09-05 + 처리량 저하   → Oracle RMAN 196 (WAS는 창 안에 완료)
평일 + 디스크 고수위         → 129
평일 + 미디어 서버 정지      → 219
```

**권한 계산 — 7개 조합 대조**

`0644 0755 4755 4644 1777 2775 0777`을 기호 표기와 대조해 전부 일치했습니다.
실행 비트 없는 setuid가 `-rwSr--r--`로 나오는 것을 포함합니다.
umask는 `022 027 002 077` 네 가지를 파일·디렉터리 기본 권한과 대조했습니다.

**디스크 예측 — 회귀 검산**

일 1.6%씩 증가하는 5일 이력을 넣고 기울기를 구한 결과 1.600%/일이 나왔습니다.
78.4%에서 90%까지 7.2일로 계산되어 수식 검산값과 일치했습니다.

**로그 분석 — 급증 탐지**

780행 중 03:40 구간에 180행을 주입한 뒤 실행해 해당 구간만 급증으로 잡아냈습니다
(218건, z=3.2). 서로 다른 4개 유형으로 정규화됐습니다.

**백업 검증 — 해시 불일치 탐지**

기준 해시를 기록한 뒤 파일을 바꿔 다시 실행해 불일치를 잡아내는 것과, 없는 파일을
FAIL로 처리하는 것을 확인했습니다.

**장애 대응 랩 — 시나리오 정합성과 채점**

6개 시나리오 모두 정답 원인과 정답 조치가 각각 하나씩이고, 필수 조사가 3건 이상이며,
모든 조사 항목이 화면 분류에 들어가는지 확인했습니다.

```
S1 웹 접속 불가      정답원인 1 정답조치 1 필수조사 4  ✓
S2 도메인 접속 실패  정답원인 1 정답조치 1 필수조사 3  ✓
S3 APP01 CPU 98%     정답원인 1 정답조치 1 필수조사 5  ✓
S4 DB01 디스크 97%   정답원인 1 정답조치 1 필수조사 4  ✓
S5 랙 온도 상승      정답원인 1 정답조치 1 필수조사 3  ✓
S6 배치 지연 연쇄    정답원인 1 정답조치 1 필수조사 4  ✓
```

채점은 세 가지 경로로 확인했습니다.
필요한 조사를 다 하고 정답을 고르면 통과하고 낭비 0건,
엉뚱한 조사만 하고 오답을 고르면 필수 조사 1/4에 낭비 4건,
조사 없이 정답만 고르면 통과하되 필수 조사 0/4로 근거가 비어 있음이 드러납니다.

**서버 콘솔 — 명령 전수 실행과 상태 연동**

서버 6대 × 명령 59건을 전부 실행해 출력에 `undefined`나 `NaN`이 섞이지 않는지
확인했습니다(59/59 정상). 장애 5종을 동시에 켠 상태에서도 모든 명령이 예외 없이
동작하고, 장애 주입 함수가 원본 데이터를 오염시키지 않는지도 확인했습니다.
장애 5종은 모두 서버 판정을 정상에서 조치 필요로 바꿉니다.
`nginx` 정지 시 서비스 상태가 failed로 바뀌면서 열린 포트가 4개에서 2개로 줄어드는 것,
`/u01` 포화 시 `df -h`에 임계 초과 표시가 붙는 것을 함께 확인했습니다.

**네트워크 경로 — 장애별 증상 분리**

다섯 가지 장애가 각각 다른 지점에서 끊기고, 동시에 다른 명령은 정상으로 나오는지를
확인했습니다. 이것이 성립해야 한 명령만으로 판단할 수 없게 됩니다.

```
방화벽 443 차단 중 ping      → 정상 (ping만 보면 놓친다)
DNS 삭제 중 IP+포트 접속     → 정상
L4 멤버 다운 중 서버 ping    → 정상 (서버는 살아 있다)
라우팅 누락 중 APP 접속      → 정상 (뒤 구간만 끊김)

traceroute 차단 지점
  방화벽 443 차단   → L4-01 에서 차단, 통과 홉 1
  라우팅 누락       → DB01 에서 차단, 통과 홉 4
```

원인 채점은 정답 1개, 오답, 복합 2개(순서 무관), 일부만 고른 경우, 장애가 없는
상태까지 다섯 가지로 확인했습니다. 장애 5종을 동시에 켜고 모든 대상 노드에
모든 명령을 실행해도 예외가 발생하지 않습니다.

**전체 회귀 검증**

네 시뮬레이터에 대해 72개 항목을 자동 검증했습니다. 시나리오 정합성, 경계 조건,
채점 로직, 장애 주입, 다중 장애 동시 적용, 범위 밖 입력 처리를 포함합니다.
검증 과정에서 실제 버그 2건(테이프 볼륨 모델, 채점 함수가 `undefined`를 반환하는 경우)을
찾아 고쳤습니다.
